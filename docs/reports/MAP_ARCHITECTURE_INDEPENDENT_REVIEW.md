# 国絵図の地図構造に関する独立調査

2026-11-03。専用作業ブランチの 64b746e と、共有ブランチの 2024e88 および読取時の作業ツリーを確認した。以下は設計提案。ゲーム実装・配信構成の変更は含まない。

## 結論

編集用の正本と、ブラウザへ配る描画データを分ける。**領域・水際・道路の正本は、出典と適用期間を持つベクター。古絵図と標高の正本は、位置合わせ情報を伴うラスター。ブラウザでは、生成済みの背景タイルに領域・道路・軍勢を重ねる。** 地域固有の補正は同じ形式のデータとして受け取り、重複の検査・適用・タイル生成は開発時に共通処理する。静的HTMLで遊べる配信形態を維持できる。

## 実例と適用範囲

| 事例 | 確認できたこと | 国絵図に取り入れること |

| OpenTTD | シナリオエディターは画像の高さマップを読み込める。ソースではゲーム内のタイル単位が独立している。[高さマップ手引き](https://wiki.openttd.org/en/Manual/Heightmap)・[ゲーム実装](https://github.com/OpenTTD/OpenTTD/blob/master/src/tile_type.h) | ラスターを制作入力にすることと、プレイ時のデータ構造を選ぶことを分ける |

## 現行コードで確認した負荷と地域差

- `game/geo.js` は1,671,047バイト、手元のgzipで510,323バイト。専用版のロード済み形状は陸地151,993頂点、管理領域56,211頂点。起動時にJavaScriptの配列を読み、地図の一部のリングを平滑化してCanvasのPath2Dにする。既存のPath2Dは再利用し、パンやズームの途中には余白付きの合成画面も再利用する。毎フレーム全頂点をJavaScriptで読み直しているという説明は現行コードと合わない。
- 生成・構文解析・初回パス化は起動コスト。タイルの取得とデコード、背景の再合成、領域の塗りと切り抜きは操作中の別のコスト。既に標高はタイル化され、キャッシュと縮尺切替がある。今回のファイル計測では、操作時の主因や高速化率までは確定できない。
- 共有版の `japan-rivers-osm.js` は天竜川・大井川の現代比較線を持つ生成データ。`castle-regions-data.js` と `castle-regions.js` は城間境界の生成データと適用を分けており、算法自体は日朝共通。児島湾の `bizen-north-shore.js` は北岸と管理領域を起動時に差し替える。役割はそれぞれ違うが、適用順・対象範囲・出典・重複の扱いが共通の契約で検査されていない。地域ごとのコードを増やすより、この契約を生成時に設ける。

## 正本、生成物、実行時の分担

| 対象 | 編集する正本 | 配布する生成物 |
| --- | --- | --- |
| 海・陸・湖・干潟と管理領域 | 共通の境界を共有する面。水域分類と管理IDは別属性。城の管理圏と史実の領有を別表に置く | 縮尺別の背景タイル。領域の動的着色には境界タイル、またはロスレスの領域IDマスク。同じ形から選択判定と外交境界も生成 |
| 河川・街道 | 河川中心線、分かる場合の幅・水面。街道は描画線と接続関係を持つネットワーク。現代比較線は独立 | 縮尺別の表示線と経路グラフ。行軍は同じ道路IDに沿う。河川の描画と渡河の交点は同じ版から生成 |
| 標高・陰影と古絵図 | DEMの格子と取得・欠測・ライセンス情報。古絵図は原画像と位置合わせの記録 | 陰影の画像タイル、必要なら標高格子。古絵図は照合用レイヤー。通常のプレイでは研究用原画像を読み込まない |
| 時点・領主・部隊 | 日付・地域ID・史料を持つ変更記録 | 日付から適用する地形版の一覧。領主・外交・部隊位置はゲーム状態から描画 |

地域差分の共通項目は `featureId`、レイヤー、対象範囲、適用期間、基準版、置換形状、出典ID、読取方法、位置精度、審査状態。地形期間は半開区間に統一し、日付が不明なら年幅や不確かさを記録する。同じ対象に同時期の差分が競合したら生成を失敗させ、明示的に統合する。香取海や児島湾では、根拠がある時点の局所形状を生成する。中間の汀線を年数に比例させて移動させるには別途根拠が必要。地形版が変わるタイルだけを生成し、影響がないタイルは共有する。

MECEの判定は出力に対して行う。描画対象の各地点には陸・水・未判定のいずれか一つ、陸地の管理は領域IDか明示的な未割当を一つとする。海上の領域選択、重複する着色、隣り合うタイルの継ぎ目、島や湖の穴の消失を検査する。干潟のように陸海が条件で変わる場所は地形分類を別に定義する。史料のない位置は審査状態として残す。この検査と生成処理は日本・朝鮮で共通とし、原資料の解像度、年代、網羅性はレイヤーの属性で区別する。

実行時は小さなマニフェスト、全景向けの低解像度タイル、表示範囲の高解像度タイルの順で読み、既存のCanvasで描画する。パン・ズーム中は親タイルを一時利用し、精細版が届いたら同じ範囲だけ差し替える。軍勢、領主変更、外交表示は独立レイヤー。領域IDマスクを採る場合は最近傍で読み、色の補間や非可逆圧縮を使わない。細い境界や小島の選択精度が不足する場合は、表示範囲のベクターに対する当たり判定を併用する。

## 解像度と量の見積もり

現行の最大倍率8、200地図単位/度では南北が約69.6m/CSS画素。東西は緯度と投影の係数で変わる。現行の表示限界 `CONT` を概算で1,854×1,315kmと置いた場合の、矩形全体を一枚として展開する量。

| 標本間隔 | 画素数の概算 | RGBA展開時 | 16bit IDのみ |
| --- | ---: | ---: | ---: |
| 70m | 約5.0億 | 約2.0GB | 約1.0GB |
| 35m | 約20億 | 約8.0GB | 約4.0GB |
| 10m | 約244億 | 約98GB | 約49GB |

圧縮後の転送量ではない。70mはDPR 1の最大倍率で約1画素、35mはDPR 2で約1物理画素に相当する。10m級の局地図は城郭や河道の資料精度と表示倍率に合わせて別に生成する。2,800×2,000物理画素の画面なら256pxタイルは境界のずれを含めて最大約108枚。RGBAでは1層約27MiBで、余白・キャッシュ・複数層は別に必要になる。全域を最細密にせず、海だけのタイルの省略、画面外タイルの解放、複数期間の共通タイル再利用を行う。圧縮率は試作で測る。

## 移行と判定

1. 既存の画面と保存データを基準に、起動時のダウンロード・構文解析・Path2D生成・初回描画、移動/ズームのp50・p95、標高表示の空白時間、メモリ、再生中のフレーム時間を計測する。同じシナリオ・同じ端末とDPRで冷/温キャッシュを分ける。
2. 既存データの最終形を生成時に再現する。先に目視で違いが出ない状態を作り、地域差分をデータへ移す。日朝の小区画を選び、同じ生成器で隣接・渡河・領域選択・縮尺の継ぎ目を検査する。
3. 地形描画の切替を独立させ、既存の城・道路・保存のIDを維持する。保存の経緯度と日内の進捗を比較し、地形版切替で海上クリック・駒の飛び・一時的な空白が出ないことを確認する。古地形の新規調査をこの移行に混ぜず、既存形状との差分が意図したものか追跡する。
4. 正本と生成物のハッシュ・出典・座標参照系をマニフェストに持つ。OSMデータは帰属表示を付け、派生データベースと描画成果物の公開条件を区分する。地理院タイルは製品別に出典と利用条件を確認する。古図は目録と画像の権利を分けて確認し、再配布条件を確認できたものを配信に含める。[OSMのライセンス案内](https://www.openstreetmap.org/copyright)・[地理院タイルの利用条件](https://maps.gsi.go.jp/help/use.html)

採否は、同一のテスト条件で操作時の時間・メモリが改善し、地形とクリック判定が揃い、既存セーブと史実イベントに回帰がないことを確認して決める。現段階の推奨は、正本と生成工程を分けること、既存Canvasに複数レイヤーを配ること。全国を一枚の画像にした場合の性能は未計測。
