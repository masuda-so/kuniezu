# 地図の再描画で画布を再利用する

## 対象と変更

main `86ec0c14`の通常配信を測定すると、ベース再構築のたびに新しいcanvasを作っていた。画布をキーに持つ海・川の描画層も使い回せず、ズームのCPU標本は画像転写に偏っていた。再描画の内容と回数を変更せず、ベースcanvasを保持し、大きさが変わった時だけ寸法を設定する。1200万画素の上限と、画面全域を覆う時だけ拡縮キャッシュを再利用する条件は維持する。

再利用では前回の描画状態を残さない。save/restoreだけの案は九州のfresh画素比較で不一致だったため採用しなかった。現在のパスもbeginPathで空にする最終案は全条件で一致した。全状態をresetする別案も画素は一致したが、単発の測定でズームScriptDuration745.1msとなったため、必要な初期化だけを行う案を残した。実行時の依存・新しいAPI要件は追加しない。

## 検証

候補の応答差替えにより、GPU有効、日本の関東・近畿・九州、1400/390幅と狭幅DPR2の7条件を確認した。実ホイール140入力、142キャッシュフレームで未被覆0。全条件で実際の再描画後の画素が一致し、再描画・拡縮を通して画面へ転写した元canvasは各条件1枚だった。全再構築は4/2/3/2/2/1/1回。DPR2のピーク縮尺は4.53、ほかは5.5。JavaScript例外0。

同じ通常配信のデータ、GPU有効、1400×950・DPR1、初期演出終了後の実縮尺5で比較した。パン24入力は919ms・ScriptDuration54.0ms・再構築0/再利用23、ズーム24入力は1965ms・ScriptDuration698.0ms・再構築4。日付・部隊は不変、縮尺5へ復帰、例外0。準備・パン後・ズーム後の3枚は通常版のPNGとバイト一致した。

基準の通常版はパン1071ms/72.1ms、ズーム1806ms/639.4ms・再構築4。単発測定ではズームが遅く、速度改善・無劣化・OS/GPUの実メモリ削減率は主張しない。確認できたのは新しいベースcanvasと付随層の再確保を避け、画面を保ったこと。全性能要望の完了とはしない。

構文・asset stamp・差分と、offline・terrain-cache・organization・work-policyの検査が通過した。生成監査は退避した64ファイルと同じSHAへ戻して確認した。通常配信への反映後の確認は別に記録する。
