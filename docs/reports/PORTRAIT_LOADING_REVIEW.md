# 肖像取得と再描画の限定点検

共有 `game/ui.js` を読み取り、候補はこの `/tmp` 以下のみへ保存した。元ファイルSHAは `source.json`。ゲームサーバー、Chrome、画像生成、全モデル検査は実行していない。

## 確認できた原因

- 追加肖像は 66 件、元ファイル計 6,084,408 bytes。起動時に `faceOf < 0` の4件（秋山虎繁・石川数正・有馬晴信・長宗我部信親）を年代や可視状態に関係なく先読みする（元ui.js 104行）。
- `portrait()` の需要取得は上限・重複URLの共有がなく、選択カード作成と地図描画からまとまって発行する（107行）。ブラウザ内部の接続上限とは別に、アプリ側には取得制御がない。
- 各 `onload` が全 `pcache` / `urlCache` を消し、地形下層も dirty にして `renderAll()` を呼ぶ。`renderAll()` は上部・年表・城欄の生成であり、選択画面では非表示領域を作り直す一方、既に作った選択カードの顔は更新しない（99/104/107/935行）。画像が続けて届く間は全肖像のCanvas切出し・Data URL再作成も繰り返す。
- `onerror` がなく、取得失敗した Image は Map に残る。`complete && !naturalWidth` の後も同じ Image を使用し、一時的な接続エラーから復旧しない。
- `result.json` の6区間は、停止/タイトル中の実描画0回、hidden模擬でloop0回。したがって現在の長時間発熱をタイトルの継続描画が原因と断定する根拠はない。3画像の通信失敗は実在し、別途HTTP再取得200なのでファイル欠落とは区別する。接続切断の原因が画像同時要求だけだったかは、この記録だけでは確定しない。

## 候補の範囲

`portrait-loading.patch` は肖像ブロックと `faceHTML()` のみ。

- 先読みを除去し、呼ばれた肖像を原画像URL単位で共有。同時取得2枚に制限（共通sprite faces.webp 1枚は別）。
- 接続失敗は500ms後に1回だけ再試行。別名も同じ取得と結果を共有。
- 120ms単位で到着をまとめ、その人物のキャッシュだけ無効化する。全地形の再描画や `renderAll()` は呼ばない。
- 表示中の `data-portrait` 要素だけ交換し、選択一覧やモーダルを再生成しない。選択・スクロール・入力中の操作を保持する。地図は静止駒層だけ更新する。
- 非表示タブでは待ち画像の取得開始と描画を止め、復帰後に再開する。進行中の最大2要求を無理に中断しない。
- sprite未到着時にfallbackを描かない判定も同じブロックで整えた。
