# 高速ズーム中の地形欠けを防ぐ

## 再現と原因

main `0adc3e11` の通常配信で、GPU有効・実ホイール操作中のbase canvasへの画像転写を観測した。キャッシュの26フレーム中6で画面全体を覆わず、最小被覆は87.1639%（最大約12.8%が単色の下地のみ）だった。最初の未被覆フレームのbase画像と、転写矩形・実カメラをローカル証拠に保存した。最初の画像は左端約1.76pxの欠けであり、最大欠けを写した画像ではない。

`drawBase` は85%以上の被覆、または再構築から120ms未満なら、画面を覆いきらない縮小画像でも使用していた。下地を単色の海で塗った上に画像を転写するため、画像の外にある地形が一時的に見えなくなる。

## 変更

転写先の四辺が画面を完全に覆う時だけ、拡縮したキャッシュを使う。足りない時は現在の地形を描き直す。同じ画像・縮尺を使い、道路や高低データの正本は変えない。不要になった120ms制御用の時刻代入も除いた。

既存の `zoom-regressions.cjs` を使い、日本の関東・近畿・九州、1400/390幅、狭幅DPR2の計7条件で検査する。旧朝鮮の戦略地図を検査対象から外し、実際の `TKRelief` とカメラが安定してから始める。実ホイール操作中の転写範囲、地図外の露出、毎回の全再構築を避けることを検査する。最終画像と再描画の比較は、400msのfontタイマー後に再構築が実際に起きたことを確認してから行う（以前の250ms待機では再描画前を比べる恐れがあった）。

## 検証の状態

7条件の候補差替え検査が通過し、キャッシュ141フレームで未被覆0・被覆100%を確認した。各条件で地図の境界が画面を覆い、最終画素のチェックサムが実際の再描画後と一致した。20ホイール入力あたりの全再構築は1〜4回。DPR2条件の実測ピークは4.53、ほか6条件は5.5だった。構文とasset stampも確認し、必要な回帰を実行中。広い要望「地図・保存の品質」の一部なので、この修正だけで対象カタログ全体を完了にしない。

作業は自分の完了済みUI用作業ツリーを再利用し、HEAD・未追跡証拠のSHAを保全してmainから別ブランチを作った。他担当のソース・担当記録は解放していない。テンプレートはasset stampだけを更新する。

同じGPU有効・実入力・実縮尺5の一回測定では、パンは23キャッシュ再利用・全再構築0、ホイール往復は全再構築2回で元の縮尺に戻った（元のmainも2回）。ScriptDurationはパン96.0ms・ズーム535.5ms、実時間は1046ms・1729ms。元のmainでは63.3ms・484.6ms、991ms・1624msだった。操作送信・観測の時間も含み、一回の候補差替え測定なので改善率や統計的な無劣化は主張しない。通常配信への反映後も確認する。

提出前の `offline.cjs`・`terrain-cache.cjs`・`map-layer-notifications.cjs`・`organization.cjs`・`work-policy.cjs`・`infrastructure.cjs` が通過した。生成監査は退避した64ファイルと同じSHAへ戻して確認した。
