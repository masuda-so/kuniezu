# 検査を減らさずにCIの時間内訳を採る

Django CIの通常のpytestへ`--durations=20`を付ける。
対象・収集規則・試験数・失敗判定・依存関係は変更せず、遅い試験と準備の時間を
既存ジョブのログに出す。追加の全件検査ジョブは作らない。

[pytest公式の時間計測](https://docs.pytest.org/en/stable/how-to/usage.html#profiling-test-execution-duration)
と、配信元venvの`python -m pytest --help`でオプションを確認した。
公式機能の利用であり、これ自体を高速化の達成とは扱わない。

既存の成功CIではpytestが6分34秒〜13分08秒を占めたが、個別試験は未測定だった。
Claudeの同じ端末での史実試験148〜150件は250〜276秒（報告値）で、これも個別内訳は無い。
初回の通常CIの実測から、重複準備の共有、実装の改善、分割可能性のどれを選ぶか判断する。
検査の省略、失敗の無視、必須チェック規則の緩和は行わない。

手元ではオプションの存在と差分を確認し、計測だけを目的とした全件の再実行はしない。
実行時間の結果はこの変更のCI完了後に確認する。

## 初回の実測

候補9a7af789の通常CI（run42750743677）は217試験が377.86秒で通過した。
上位は、早島の地形保持10.80秒、史実の過去版保持9.86秒、CODH実入力9.78秒。
複数回取り込みを行う史実試験が9秒台、通常の取り込みを行う試験も3.7秒前後だった。
地理の検査だけを原因とは扱わず、繰り返す取り込み処理も調べる。

隔離した新規SQLiteへの1回のcProfile付き取り込みは7.086秒。
Importer.known_asは2,795呼出し・累積1.116秒、labelは1,607呼出し・0.861秒、
take_partは1,425呼出し・0.813秒だった。これらの累積時間は呼出し関係で重なるので加算しない。
計測器の負荷を含むため、この7.086秒をCIの速度や通常時の単価とは比較しない。

次はClaudeが1回のImporter内で重複するキー・名前・参加・根拠関係の照会を避ける候補を担当する。
同一の固定入力でfresh/reimportの時間と全対象・関係・記録版を比較し、
中身の完全一致と試験通過を確かめてから改善の採否を判断する。性能改善はまだ未達成。
