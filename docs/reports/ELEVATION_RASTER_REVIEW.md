# 標高画像の配布方針と出典確認

現行の `game/terrain-tiles.js` は外部の地理院 `dem_png` と AWS Terrarium、一部のローカル概観タイルを読み、ブラウザで標高を復号して陰影を作る。画面用の陰影PNGは開発時に生成し、領域画像と同じ原点・範囲・解像度・タイル番号で配布する案を検討する。標高値の画像と描画用の陰影は用途と再利用性が異なるため、別成果として審査する。

| 入力 | 配布前に確認すること |
|---|---|
| 国土地理院の標高タイル | [利用規約](https://web1.gsi.go.jp/kikakuchousei/kikakuchousei40182.html)に従って出所と加工を明記する。[測量成果の事例集](https://www.gsi.go.jp/LAW/2930-sample.html)は標高データを使った陰影段彩図を第30条の使用承認の対象例とする。[利用手続フロー](https://www.gsi.go.jp/common/000221848.pdf)の陰影表記例もあるため、出力が陰影のみの場合と、測地座標付き標高格子や地形段彩を配布する場合を分け、今回の出力仕様を示して国土地理院に該当性を確認する。非営利だけで申請不要としない。 |
| AWS Terrain Tiles / Terrarium | RGBは符号化方式。AWSの[データ登録](https://registry.opendata.aws/terrain-tiles/)は[Tilezenの帰属表](https://github.com/tilezen/joerd/blob/master/docs/attribution.md)を条件として参照する。[入力資料一覧](https://github.com/tilezen/joerd/blob/master/docs/data-sources.md)にあるように原資料が複数で、ズームと地域によって混ざる。実際の取得範囲・ズーム・取得日・利用可能な原資料識別情報を保存し、対象タイルの帰属と再配布条件を確認する。 |
| Copernicus DEM | Terrarium全体をCopernicusと扱わない。別の入力として採る場合に配布元・製品・版・帰属条件を特定して比較する。 |

陰影生成の条件は、隣接タイルを1画素以上読んで境界で勾配が切れないこと、欠測を海と混同しないこと、日本・朝鮮に同じ勾配と色付けを適用すること。出力マニフェストに入力製品・使用日・出典表記・座標・解像度・NoData・ハッシュを残す。切り替え前に国境・海岸をまたぐタイルの隙間、ズームアウト直後の欠落、主要地点の標高と実画面を検査する。

今回は規約と現行経路の調査。新しい標高画像の取得・配布は実施していない。既存の `tools/map/build-height-raster.py` は保有する標高PNGの格子変換を試すツールで、配布の承認を示すものではない。

## 事前生成の実装

`python3 tools/map/build-hillshade-raster.py <共通格子のmanifest.json> <16bit標高タイルのディレクトリ> <新規出力ディレクトリ>`。PillowとNumPyを使用。既存の配色を使い、隣接タイルの境界画素を参照して勾配を計算する。欠測画素は透明、隣接欠測では有効な片側を使う。経度方向の画素間隔は緯度に応じて補正する。入力格子・標高画像のハッシュと寸法を検証し、出力マニフェストに元の標高マニフェストと画像のハッシュを記録する。

合成標高を1枚と4枚に分けて変換し、端数タイル・継ぎ目・欠測を含む全56画素でRGBA値が一致した。実地の配布画像とブラウザ接続は別工程。

手元にあった早島の地理院標高PNG（Z14・6枚）で、旧格子と拡張作業版の双方に標高と陰影を事前生成した。出力タイル番号は `9-8 → 9-12`、有効な2,360画素と欠測の透明部を含む陰影PNGはバイト単位で一致。Y原点の4タイル移動が描画内容を変えないことを、この範囲で確認した。生成物は一時ディレクトリに留め、配布対象に含めていない。

`build-height-raster.py --provider terrarium` は手元のTerrarium PNGを既存の標高格子と同じ投影・採取処理へ通す。16bit符号化では海底標高も保持できるよう0.5m刻みとし、地理院の0.25m刻みは維持。符号化はマニフェストで判別し、陰影生成器は両方式を同じ処理で読む。リポジトリ内の朝鮮周辺Z6画像1枚から36枚の陰影試験タイルを生成した。別のZ6タイルも入力に加え、ソウル付近の画素で入力復号と出力の差が0.25m以内であることを確認した。Z6入力の細部が100m精度になるという意味ではない。地理院の早島出力は既存版とPNGが一致した。

継ぎ目の再検査は `python3 tools/checks/hillshade-raster.py`。合成データだけを使い、横・縦の境界、端数タイル、境界付近の欠測を含む画像を1枚出力と4枚出力で全画素比較する。ソウル付近の比較値は入力・出力とも61.0m（Z6の画素値）。

標高変換に `--factor 1|4|8` を指定できる。陰影生成は入力の倍率と格子寸法を検証し、その間隔で勾配を求める。既存の早島入力を使った試験では100mで2,360画素、400mで150画素、800mで35画素。

## Copernicus GLO-90

取得済みの239枚はファイル名の `COG_30` にかかわらず、緯度方向の標本間隔が3秒のGLO-90。変換器はGeoTIFFタグのWGS84・PixelIsPoint・1度のフットプリントと、取得時のSHA-256を照合する。各格子中心を含む1度区画で最近傍点を採取し、欠測を0にする。既存の陰影生成器へ接続でき、両マニフェストに製品・取得日・利用条件を、標高側に全入力ハッシュを保持する。

`python3 tools/map/build-copernicus-height.py <共通格子manifest> <取得済みディレクトリ> <出力先> --acquired 2026-11-03 --factor 1`。倍率4・8も同様。配布には公式のGLO-90ライセンス第6条(b)の加工物通知と同(c)の免責文を使う。出力マニフェストに両方を含める。 [Copernicus公式ライセンス、GLO-90第6条](https://dataspace.copernicus.eu/sites/default/files/media/files/2025-06/copernicus_contributing_mission_data_access_v2_cop_dem_licenses.pdf)

### 生成物のカバレッジ

取得済み239枚から100mで310、400mで32、800mで9枚ずつの標高PNGと陰影PNGを生成した。 `python3 tools/checks/elevation-coverage.py <game/map> <生成ディレクトリ>` で基準格子と出力ハッシュを照合し、各標高画素の有無と陰影のアルファ値が全出力で一致することを検査した。

| 格子 | 基準の陸画素 | 標高欠測 | 城・中立地等へ割当済みの陸で欠測 |
|---|---:|---:|---:|
| 100m | 111,099,421 | 28 | 0 |
| 400m | 6,944,680 | 1 | 0 |
| 800m | 1,736,298 | 0 | 0 |

欠測の28画素は東経140.3537〜140.3582度・北緯29.8075〜29.8129度の未割当の陸。入力に東経140度・北緯29度の1度タイルはない。海上保安庁の孀婦岩の概位には近いが、同庁の標高点とはずれているため、岩の輪郭や標高を補間せず、地形形状側の確認候補とする。 [海上保安庁・孀婦岩](https://www1.kaiho.mlit.go.jp/kaiikiDB/kaiyo17-2.htm)

### 投影位置と配布画像の独立照合

日本・朝鮮・大陸の代表点から出力格子の画素を求め、画素中心を経緯度へ逆投影した。入力GeoTIFFのタイポイントと画素間隔から元の標本を引き、16bit PNGを復号した値と比較した。地点は投影検査用の任意点で、都市の代表標高を示すものではない。

| 検査地点（東経、北緯） | 100m 入力→出力 | 400m 入力→出力 | 800m 入力→出力 |
|---|---:|---:|---:|
| 京都（135.7600、35.0200） | 55.333→55.25m | 52.194→52.25m | 50.470→50.50m |
| ソウル（126.9780、37.5665） | 30.192→30.25m | 34.647→34.75m | 41.666→41.75m |
| 瀋陽（123.4300、41.8000） | 51.388→51.50m | 52.188→52.25m | 46.228→46.25m |

9標本すべてが0.25m刻みの丸め上限0.125m以内。縮尺によって格子中心の位置が異なるため、各縮尺の入力値も異なる。

統合作業ツリーの `b5f0fb9` 上で生成された配布用WebPも、生成元の陰影PNGと全351枚を照合した。配布マニフェストのハッシュ、画像寸法、全アルファ画素が一致。有効画素のRGBチャンネルの平均絶対差は100mで1.289、400mで1.417、800mで1.413（各チャンネル0〜255）。この検査は配布画像の変換までを対象とし、ブラウザの読込順序やズーム時の切替は別の検査対象とする。

専用Chromeで統合側のローカルHTMLを開き、実行時の `TKRelief.paint` をオフスクリーンCanvasで検証した。京都・ソウル・瀋陽の3地点それぞれで、粗い画像を取得済みの状態からズーム0.6→6→0.6を連続して指定し、その後ズーム6の読込完了を待った。3地点すべてで、細かい画像の初回は読込中でも中心画素のアルファ値が255。縮小直後も255で読込済み、拡大側は読込完了後に255。JavaScript例外0。ローカルファイルでの描画関数の検査であり、HTTP配信や地図全体の操作・描画性能は対象外。

地図画面でも新規1560年シナリオから近畿と朝鮮を表示し、カメラ倍率0.6→5→0.6を実行した。両地域で詳細タイルの読込中から完了への切替を観測し、縮小後の最初の描画で粗いタイルが読込済みだった。6画面を取得し、朝鮮詳細画面では河川、街道、陰影の重なりを目視確認した。JavaScript例外0。統合側のローカルHTMLを使用し、地図のカメラAPIで操作した。マウスホイール入力とフレーム時間は測定対象に含めていない。

統合コミット `beecd46` の配布用WebPを再検査するには、Pillow（WebP対応）のある環境で `python3 tools/checks/relief-webp.py <統合側のgame/map> <生成ディレクトリ>` を実行する。3縮尺のタイル一覧、元PNGとWebPのハッシュ、寸法、透明度の全画素を照合する。統合版の310・32・9枚で通過した。

### 生成と配布の担当境界

標高・陰影の生成器と独立検査は Codex 側、配布用WebPへの変換器と描画の接続は統合側にある。統合側の `838d5ee` に変換器 `tools/map/encode-relief-webp.cjs` が入った。再生成時は同じ格子マニフェストを3縮尺で共有し、検証済み入力の `SHA256SUMS` と取得日を引き継ぐ。

以下は生成器と検査がそろった作業ツリーでの手順。先に `map_dir` を統合側の `game/map`、`dem_input` を取得済みGeoTIFFのディレクトリに設定する。PythonにはPillowとNumPyが必要。

```sh
shade_root="$(mktemp -d)"
for factor in 1 4 8; do
  python3 tools/map/build-copernicus-height.py "$map_dir/manifest.json" \
    "$dem_input" "$shade_root/height-$factor" --acquired 2026-11-03 --factor "$factor" &&
  python3 tools/map/build-hillshade-raster.py "$map_dir/manifest.json" \
    "$shade_root/height-$factor" "$shade_root/shade-$factor" || break
done
python3 tools/checks/elevation-coverage.py "$map_dir" "$shade_root"
```

カバレッジ検査を通過した出力を、変換器を含む専用の作業ツリーで `SHADE_ROOT="$shade_root" node tools/map/encode-relief-webp.cjs` に渡す。変換器は自分の作業ツリーの `game/map` に書き込む。初版の変換器は既存画像のディレクトリを先に消すため、配信中の作業ツリーで実行しない。変換先の `game/map` を引数にして `python3 tools/checks/relief-webp.py <変換先のgame/map> "$shade_root"` を通し、全縮尺の格子・出典情報と全タイルの一致を確認してから配布する。

郡の割当だけを更新すると領域マニフェストのハッシュは変わる。生成時のマニフェストを `--source-grid` に渡すと、元のハッシュによる出典照合に加え、投影・原点・画素間隔・タイル寸法・各縮尺の格子寸法を現在の地図と照合する。郡データ反映中の地図で全351枚が通過し、原点を1画素分ずらした検査入力は拒否した。
